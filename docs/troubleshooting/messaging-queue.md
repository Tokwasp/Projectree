# 비동기 메시징 큐 도입

> 노드 생성 요청이 유실되는 문제를 AWS SQS 기반 비동기 메시징 큐로 해결한 과정

---

## 1. 문제 상황

노드 생성 신청 시 **간혹 요청이 처리되지 않는 경우**가 발생했습니다.

- 사용자는 신청에 성공한 것처럼 보이지만, 실제로는 노드가 생성되지 않음
- 재현 빈도가 낮아 클라이언트 로그만으로는 원인 파악이 어려움

<!-- 이미지: 요청은 성공했으나 노드가 생성되지 않은 화면 -->

---

## 2. 관련 비즈니스 로직

| 요구사항 | 설명 |
| --- | --- |
| 노드 / 회의록 생성 | 회원은 화상 회의 종료 후 노드와 회의록 생성을 체크할 수 있다 |
| 실시간 알림 | 노드 혹은 회의록 생성 시 실시간 알림을 받는다 |

즉, **생성 작업의 완료가 알림 전송까지 이어지기 때문에 작업 유실은 곧 사용자 경험의 단절**로 이어집니다.

<!-- 이미지: 회의 종료 → 생성 체크 → 알림 수신 사용자 플로우 -->

---

## 3. 기존 구조

사용자가 노드 생성을 요청하면 **HTTP 통신을 통해 별도로 분리된 Python 모듈에 작업을 보내고, 작업 완료 후 콜백을 받는 구조**였습니다.

해당 작업은 평균 **30초**가 소요되기 때문에, 요청 스레드를 점유하지 않도록 Spring의 `@Async`를 활용해 비동기로 처리했습니다.

```
[Client] → [Spring Server] --(HTTP, @Async)--> [Python Module]
                  ↑                                   │
                  └───────────── callback ────────────┘
```

<!-- 이미지: 기존 아키텍처 다이어그램 -->

### 문제 지점

CloudWatch 로그를 분석하는 과정에서 **일부 요청이 처리되지 않는 문제**를 확인했습니다.

작업 요청이 애플리케이션 서버의 메모리(스레드 풀) 안에만 존재했기 때문에, 요청이 유실되면 복구할 수단이 없었습니다.

<!-- 이미지: CloudWatch 로그 캡처 (요청 로그는 있으나 완료 로그가 없는 구간) -->

---

## 4. 해결 과정

### 4-1. 재시도 로직 검토

가장 먼저 재시도 로직을 검토했습니다.

- ✅ 일시적인 통신 실패는 복구 가능
- ❌ **서버가 종료되는 경우 작업 요청 자체를 보장하기 어려움**

재시도 대상인 요청 정보 역시 애플리케이션 서버 메모리에 있었기 때문에, 배포·스케일 인·비정상 종료 시 함께 사라진다는 한계가 있었습니다.

### 4-2. 메시징 큐 도입 결정

따라서 **작업 요청 자체를 애플리케이션 서버와 분리된 공간에 안전하게 보관할 필요**가 있었고, 이를 해결하기 위해 메시징 큐를 도입했습니다.

### 4-3. 기술 선정

| 후보 | 강점 | 채택하지 않은 이유 |
| --- | --- | --- |
| **Kafka** | 대용량 이벤트 스트리밍 | 현재 서비스 규모에는 오버 엔지니어링 |
| **RabbitMQ** | 유연한 라우팅 | 현재 구조에서는 라우팅 기능이 필요하지 않음 |
| **AWS SQS** ✅ | 관리형 서비스, 운영 부담 최소 | — |

별도의 브로커를 직접 운영하는 대신 **AWS 관리형 서비스인 SQS를 활용하여 운영 부담을 줄이고자** 했습니다.

<!-- 이미지: Kafka / RabbitMQ / SQS 비교 표 또는 선정 기준 다이어그램 -->

### 4-4. DLQ 구성

마지막으로 반복적으로 처리되지 않는 작업은 **3회 이상 처리에 실패할 경우 DLQ(Dead Letter Queue)로 이동**하도록 설정하여, 일반적인 작업과 분리해 추적할 수 있도록 구성했습니다.

<!-- 이미지: 개선된 아키텍처 다이어그램 (SQS + DLQ) -->

---

## 5. 개선 결과

```
[Client] → [Spring Server] → [SQS] → [Python Module]
                                │
                          3회 실패 시
                                ↓
                             [DLQ]
```

- 작업 요청이 **애플리케이션 서버 외부에 영속**되어, 서버가 종료되어도 유실되지 않음
- 소비자(Python 모듈)의 장애 상황에서도 큐에 작업이 남아 있어 복구 후 이어서 처리 가능
- 반복 실패 작업이 DLQ로 격리되어 **정상 처리 흐름에 영향을 주지 않고 원인 추적 가능**
