# 서버 배포 중 발생한 회의 분석 요청 유실 문제를 SQS·DLQ 도입으로 해결

## 문제 상황 아키텍처

```text
[Client] → [Spring 서버] --(HTTP, @Async)--> [Python 분석 서버]
                 ↑                                  │
                 └──────────── 완료 콜백 ────────────┘
```

## 문제 상황

회의 분석 요청을 보내는 도중 서버를 재배포하자, **요청이 유실되어 분석 결과가 생성되지 않는 현상**을 발견했습니다.

## 원인 분석

기존에는 Spring `@Async`를 통해 Python 분석 서버에 HTTP 요청을 전달하는 구조였습니다.
그러나 **작업 요청을 별도로 저장하지 않아**, 서버 종료나 통신 장애가 발생하면 실패한 요청을 다시 처리하기 어려웠습니다.

| 상황 | 결과 |
|---|---|
| API 서버 재배포·종료 | 처리 중이던 요청이 함께 사라짐 |
| 분석 서버 장애·재시작 | 처리 중이던 요청을 다시 받을 방법이 없음 |
| 일시적인 통신 장애 | 요청이 분석 서버에 전달되지 않음 |

## 해결 과정

### DB 저장 + 스케줄러 재시도 검토

요청 유실을 방지하기 위해 **DB에 작업을 저장하고 스케줄러로 재시도**하는 방식을 검토했습니다.
그러나 다중 서버 환경에서 **중복 실행 방지와 실패 처리 로직을 직접 구현**해야 하는 부담이 있었습니다.

### SQS · DLQ 도입

이를 해결하기 위해 **AWS SQS를 도입해 분석 요청을 큐에 저장**하고, Python 분석 서버가 메시지를 가져와 처리하도록 변경했습니다.
또한 **3회 이상 실패한 요청은 DLQ로 분리**해 실패 원인을 추적하고 재처리할 수 있도록 구성했습니다.

```text
[Client] → [Spring 서버] → [SQS] → [Python 분석 서버]
                             │
                        3회 실패 시
                             ↓
                           [DLQ]
```

## 결과

- SQS에 분석 요청을 보관해 **서버 재배포나 장애 발생 시에도 요청을 재처리**할 수 있도록 개선했습니다.
- 반복 실패한 요청은 **DLQ로 분리해 원인을 추적**할 수 있도록 했습니다.

## 배운 점

- 원격 환경에서 SQS를 테스트하던 중 **메시지가 수신되지 않는 문제**가 발생했습니다. 원인을 확인한 결과, 동료가 로컬 환경에서 같은 SQS를 사용해 메시지를 가져가고 있었기 때문이었습니다.
- 이를 계기로 **CloudWatch에 메시지 수신·처리·완료 로그를 추가**해 작업 흐름을 추적할 수 있도록 개선하며, 비동기 시스템에서 로그 관리의 중요성을 체감했습니다.
