# SQS 도입으로 회의 분석 요청 유실 방지

> 1분 가까이 걸리는 회의 분석 작업이 서버 배포·장애 중에도 사라지지 않도록, 작업 요청을 메시징 큐에 보관하는 구조로 설계했습니다.

## 배경

Projectree는 화상 회의가 끝나면 사용자가 선택한 산출물(회의록 요약, 노드)을 AI로 생성하고, 완료되면 실시간 알림을 보냅니다.

```text
회의 종료 → 산출물 선택 → 녹음 음성 분석(STT + LLM) → 회의록·노드 생성 → 완료 알림
```

이 분석 작업은 일반적인 API 요청과 성격이 달랐습니다.

| 특징 | 내용 |
|---|---|
| **오래 걸림** | 노드 생성까지 직접 측정해 보니 **약 1분** 소요 |
| **다른 서버에서 처리** | API 서버(Spring, ECS Fargate)와 분석 서버(Python, EC2)가 분리됨 |
| **서버가 자주 바뀜** | API 서버는 여러 대로 운영되고, 배포 때마다 새 서버로 교체됨 |

## 문제 상황

가장 단순한 방법은 API 서버가 분석 서버에 HTTP로 작업을 보내고, 1분을 기다리지 않도록 `@Async`로 백그라운드에서 처리하는 것입니다.

```text
[Client] → [Spring 서버] --(HTTP, @Async)--> [Python 분석 서버]
                 ↑                                  │
                 └──────────── 완료 콜백 ────────────┘
```

하지만 이 구조에서는 **작업 요청이 API 서버의 메모리에만 존재**합니다. 1분이라는 처리 시간 동안 아래 상황이 하나라도 생기면 요청이 그대로 사라집니다.

| 상황 | 결과 |
|---|---|
| API 서버 배포·교체 | 메모리에 있던 작업 요청이 함께 사라짐 |
| 분석 서버 장애·재시작 | 처리 중이던 요청을 다시 받을 방법이 없음 |
| 일시적인 네트워크 오류 | 요청이 전달되지 않음 |

사용자 입장에서는 **"회의록 생성"을 눌렀는데 결과도, 알림도 끝내 오지 않는 상황**이 됩니다. 실패했다는 사실조차 알 수 없어 다시 시도할 수도 없습니다.

## 해결 과정

### 1차 검토: 실패하면 다시 보내기 (재시도)

요청이 실패하면 잠시 뒤 다시 보내는 방법을 먼저 검토했습니다.

- ✅ 네트워크가 잠깐 끊긴 경우는 다시 보내면 해결됨
- ❌ 하지만 "다시 보낼 요청 목록"도 API 서버가 들고 있어서, **배포로 서버가 교체되면 목록째 사라짐**

→ 서버가 꺼져도 남아 있는 **별도의 장소에 요청을 보관**해야 했습니다.

### 2차 검토: 메시징 큐 도입

API 서버는 작업을 큐에 넣기만 하고, 분석 서버가 큐에서 꺼내 처리하는 구조로 바꿨습니다.
작업이 끝나기 전까지 메시지가 큐에 남아 있기 때문에, **어느 쪽 서버가 내려가도 다시 살아난 서버가 이어서 처리**할 수 있습니다.

```text
[Client] → [Spring 서버] → [SQS] → [Python 분석 서버]
                             │
                        3회 실패 시
                             ↓
                           [DLQ]
```

### 기술 선정

| 후보 | 강점 | 채택하지 않은 이유 |
|---|---|---|
| Kafka | 대용량 이벤트 스트리밍 | 현재 서비스 규모에는 과한 구성 |
| RabbitMQ | 유연한 라우팅 | 라우팅 기능이 필요 없고, 브로커를 직접 운영해야 함 |
| **AWS SQS** ✅ | AWS 관리형 서비스, 운영 부담 최소 | — |

이미 AWS 위에서 서비스를 운영하고 있었고, 필요한 것은 "작업을 잃지 않고 전달하는 것"이었기 때문에 **브로커를 직접 운영할 필요가 없는 SQS**를 선택했습니다.

### DLQ로 실패 작업 분리

같은 작업이 계속 실패하면 큐에서 무한히 재시도되며 다른 작업까지 지연시킬 수 있습니다.
그래서 **3회 이상 처리에 실패한 메시지는 DLQ(Dead Letter Queue)로 옮겨**, 정상 작업과 분리해 원인을 따로 추적할 수 있게 했습니다.

## 결과

| 상황 | 직접 호출 (`@Async` + HTTP) | SQS 적용 |
|---|---|---|
| API 서버 배포·교체 | 작업 요청 유실 | 큐에 남아 있어 유실 없음 |
| 분석 서버 장애 | 처리 중 요청 유실 | 복구 후 큐에서 이어서 처리 |
| 반복 실패 작업 | 추적 불가 | DLQ로 분리해 원인 확인 |

- 약 1분 걸리는 분석 작업을 **서버 상태와 관계없이 끝까지 처리**할 수 있게 됐습니다.
- API 서버와 분석 서버가 큐를 사이에 두고 분리되어, **한쪽을 배포하거나 장애가 나도 다른 쪽에 영향을 주지 않습니다.**

## 배운 점
- **로그의 중요성을 체감했습니다.** 큐 연동을 테스트하던 중 메시지가 사라진 것처럼 보이는 일이 있었는데, 원인은 로컬과 원격 서버가 같은 큐를 함께 구독하고 있어 **로컬 서버가 메시지를 먼저 가져가 처리한 것**이었습니다. 하지만 처리 로그가 없어 이를 확인하기까지 오래 걸렸고, 이후 메시지 수신·처리·완료 같은 **핵심 지점마다 CloudWatch에 로그를 남기도록** 해 메시지의 흐름을 바로 추적할 수 있게 했습니다.
