# SQS 도입으로 회의 분석 요청 유실 방지

> 서버 재배포 중 일부 회의 분석 요청이 처리되지 않는 문제를, 작업 요청을 메시징 큐에 보관하는 구조로 개선했습니다.

## 상황

화상 회의가 끝나면 사용자가 선택한 산출물(회의록 요약, 노드)을 AI로 생성하고, 완료되면 실시간 알림을 보내는 기능을 개발했습니다.

```text
회의 종료 → 산출물 선택 → 녹음 음성 분석(STT + LLM) → 회의록·노드 생성 → 완료 알림
```

회의 분석 기능을 테스트하던 중 서버를 재배포했을 때, **일부 분석 요청이 정상적으로 처리되지 않아 결과가 생성되지 않는 현상**을 발견했습니다.
사용자는 회의록 생성을 요청했지만 결과도, 알림도 받지 못하는 상태가 됩니다.

## 원인 분석

기존에는 Spring `@Async`를 통해 Python 분석 서버에 HTTP 요청을 전달하는 구조였습니다.

```text
[Client] → [Spring 서버] --(HTTP, @Async)--> [Python 분석 서버]
                 ↑                                  │
                 └──────────── 완료 콜백 ────────────┘
```

이 구조에서는 **작업 요청을 별도로 저장하지 않기 때문에**, 서버 종료나 통신 장애가 발생하면 실패한 요청을 다시 처리하기 어려웠습니다.

| 상황 | 결과 |
|---|---|
| API 서버 재배포·종료 | 메모리에서 대기·처리 중이던 요청이 함께 사라짐 |
| 분석 서버 장애·재시작 | 처리 중이던 요청을 다시 받을 방법이 없음 |
| 일시적인 통신 장애 | 요청이 분석 서버에 전달되지 않음 |

## 해결 과정

### 1차 검토: DB 저장 + 스케줄러 재시도

요청 유실을 방지하기 위해 **작업을 DB에 저장하고 스케줄러로 재시도**하는 방식을 먼저 검토했습니다.
요청이 DB에 남아 유실은 막을 수 있지만, 다중 서버 환경에서 아래 로직을 직접 구현해야 하는 부담이 있었습니다.

| 직접 구현해야 하는 기능 | 필요한 이유 |
|---|---|
| 중복 실행 방지 | API 서버가 여러 대라 같은 작업을 동시에 재시도할 수 있음 |
| 실패 처리 | 계속 실패하는 작업이 무한히 반복되지 않도록 재시도 제한·분리가 필요함 |

### 2차: AWS SQS 도입

이를 해결하기 위해 **AWS SQS를 도입해 분석 요청을 큐에 저장**하고, Python 분석 서버가 메시지를 가져와 처리하도록 변경했습니다.
또한 **3회 이상 실패한 요청은 DLQ(Dead Letter Queue)로 분리**해 실패 원인을 추적하고 재처리할 수 있도록 구성했습니다.

```text
[Client] → [Spring 서버] → [SQS] → [Python 분석 서버]
                             │
                        3회 실패 시
                             ↓
                           [DLQ]
```

| 후보 | 강점 | 채택하지 않은 이유 |
|---|---|---|
| Kafka | 대용량 이벤트 스트리밍 | 현재 서비스 규모에는 과한 구성 |
| RabbitMQ | 유연한 라우팅 | 라우팅 기능이 필요 없고, 브로커를 직접 운영해야 함 |
| **AWS SQS** ✅ | AWS 관리형 서비스, 운영 부담 최소 | — |

## 테스트 및 검증

큐 연동 중 **메시지가 사라진 듯 보이는 현상**이 있었습니다.
조사 결과, 로컬 워커와 원격 워커가 **같은 큐를 소비**하고 있어 로컬 워커가 메시지를 먼저 가져가 처리한 것이 원인이었습니다.

이후 **CloudWatch에 메시지 수신·처리·완료 로그를 추가**해, 어떤 워커가 어떤 메시지를 처리했는지 처리 경로를 추적할 수 있도록 했습니다.

## 결과

| 상황 | 기존 (`@Async` + HTTP) | SQS 적용 후 |
|---|---|---|
| API 배포·분석 서버 재시작 | 요청을 다시 처리하기 어려움 | 요청이 큐에 유지되어 영향을 덜 받음 |
| 반복 실패 작업 | 실패 원인 추적이 어려움 | DLQ로 분리해 확인·재처리 가능 |

- API 배포·분석 서버 재시작에 영향을 덜 받도록 **요청을 큐에 유지**하는 구조를 구축했습니다.
- 작업 실패를 **DLQ에서 분리해 확인**할 수 있는 구조를 구축했습니다.
