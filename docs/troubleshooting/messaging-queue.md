# SQS 도입으로 회의 분석 요청 유실 방지

> 1분 가까이 걸리는 회의 분석 작업이 서버 배포·장애 중에도 사라지지 않도록, 작업 요청을 메시징 큐에 보관하는 구조로 설계했습니다.

## 배경

화상 회의가 끝나면 사용자가 선택한 산출물(회의록 요약, 노드)을 AI로 생성하고, 완료되면 실시간 알림을 보내는 기능을 개발했습니다.

```text
회의 종료 → 산출물 선택 → 녹음 음성 분석(STT + LLM) → 회의록·노드 생성 → 완료 알림
```

이 분석 작업은 일반적인 API 요청과 성격이 달랐습니다.

| 특징 | 내용 |
|---|---|
| **긴 처리 시간** | 노드 생성까지 직접 측정한 결과 **약 1분** 소요 |
| **서버 분리** | API 서버(Spring, ECS Fargate)와 분석 서버(Python, EC2)가 별도로 동작 |
| **잦은 서버 교체** | API 서버는 여러 대로 운영되며, 배포할 때마다 새 서버로 교체 |

## 문제 상황

가장 단순한 방법은 API 서버가 분석 서버에 HTTP로 작업을 요청하고, 1분을 기다리지 않도록 `@Async`로 백그라운드에서 처리하는 것이었습니다.

```text
[Client] → [Spring 서버] --(HTTP, @Async)--> [Python 분석 서버]
                 ↑                                  │
                 └──────────── 완료 콜백 ────────────┘
```

하지만 이 구조에서는 **작업 요청이 API 서버의 메모리에만 존재**합니다. 1분의 처리 시간 동안 아래 상황 중 하나만 발생해도 요청이 유실될 수 있었습니다.

| 상황 | 결과 |
|---|---|
| API 서버 배포·교체 | 메모리에 있던 작업 요청이 함께 사라짐 |
| 분석 서버 장애·재시작 | 처리 중이던 요청을 다시 받을 방법이 없음 |
| 일시적인 네트워크 오류 | 요청이 분석 서버에 전달되지 않음 |

이 경우 사용자는 **회의록 생성을 요청했지만 결과도, 알림도 받지 못하게** 됩니다. 실패 사실조차 알 수 없어 다시 시도할 수도 없다는 점이 가장 큰 문제라고 판단했습니다.

## 해결 과정

### 1차 시도: DB 저장 + 스케줄러 재시도

작업 요청을 DB에 저장하고, 스케줄러가 주기적으로 확인해 **처리되지 않은 작업을 다시 실행**하는 방법을 먼저 검토했습니다.
요청이 DB에 남아 유실은 막을 수 있었지만, 아래 기능을 모두 직접 구현해야 했습니다.

| 직접 구현해야 하는 기능 | 필요한 이유 |
|---|---|
| 중복 실행 방지 (락) | API 서버가 여러 대라 같은 작업을 동시에 재시도할 수 있음 |
| 타임아웃 기준 | "처리 중"인지 "장애로 멈춘 것"인지 구분해야 함 |
| 재시도 제한 · 실패 분리 | 계속 실패하는 작업이 무한히 반복되지 않아야 함 |

→ 메시징 큐가 기본으로 제공하는 기능을 직접 만드는 것과 같다고 판단해, **메시징 큐를 도입**하기로 했습니다.

### 2차 시도: 메시징 큐 도입

API 서버는 작업을 큐에 넣기만 하고, 분석 서버가 큐에서 작업을 가져가 처리하도록 구조를 변경했습니다.
메시지는 처리가 완료될 때까지 큐에 남아 있기 때문에, **어느 서버가 중단되더라도 복구된 서버가 이어서 처리**할 수 있습니다.

```text
[Client] → [Spring 서버] → [SQS] → [Python 분석 서버]
                             │
                        3회 실패 시
                             ↓
                           [DLQ]
```

메시징 큐는 다음 기준으로 선정했습니다.

| 후보 | 강점 | 채택하지 않은 이유 |
|---|---|---|
| Kafka | 대용량 이벤트 스트리밍 | 현재 서비스 규모에는 과한 구성 |
| RabbitMQ | 유연한 라우팅 | 라우팅 기능이 필요 없고, 브로커를 직접 운영해야 함 |
| **AWS SQS** ✅ | AWS 관리형 서비스, 운영 부담 최소 | — |

이미 AWS에서 서비스를 운영하고 있었고 필요한 기능은 "작업을 잃지 않고 전달하는 것"이었기 때문에, **브로커를 직접 운영할 필요가 없는 SQS**를 선택했습니다.

### 실패 작업 분리: DLQ 구성

같은 작업이 계속 실패하면 큐에서 무한히 재시도되어 다른 작업까지 지연될 수 있습니다.
이를 막기 위해 **3회 이상 처리에 실패한 메시지는 DLQ(Dead Letter Queue)로 이동**하도록 설정해, 정상 작업과 분리하고 실패 원인을 따로 추적할 수 있도록 구성했습니다.

## 결과

| 상황 | 직접 호출 (`@Async` + HTTP) | SQS 적용 |
|---|---|---|
| API 서버 배포·교체 | 작업 요청 유실 | 큐에 보관되어 유실 없음 |
| 분석 서버 장애 | 처리 중 요청 유실 | 복구 후 큐에서 이어서 처리 |
| 반복 실패 작업 | 추적 불가 | DLQ로 분리해 원인 확인 |

- 약 1분이 걸리는 분석 작업을 **서버 상태와 관계없이 끝까지 처리**할 수 있게 되었습니다.
- API 서버와 분석 서버가 큐를 사이에 두고 분리되어, **한쪽을 배포하거나 장애가 발생해도 다른 쪽에 영향을 주지 않는 구조**를 만들었습니다.

## 배운 점

- **로그의 중요성을 체감했습니다.** 큐 연동을 테스트하던 중 메시지가 사라진 것처럼 보이는 문제가 있었는데, 원인은 로컬과 원격 서버가 같은 큐를 구독하고 있어 **로컬 서버가 메시지를 먼저 가져가 처리한 것**이었습니다. 처리 로그가 없어 원인을 찾는 데 오랜 시간이 걸렸고, 이후 메시지 수신·처리·완료 등 **핵심 지점마다 CloudWatch 로그를 남기도록** 개선해 메시지 흐름을 바로 추적할 수 있게 했습니다.
