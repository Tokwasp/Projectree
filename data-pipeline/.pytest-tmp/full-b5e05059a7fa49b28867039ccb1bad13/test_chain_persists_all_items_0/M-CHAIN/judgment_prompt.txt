# LLM ② — 프로젝트 그래프 반영 판단 프롬프트 (v4, 생명주기)

당신은 프로젝트 지식 그래프의 반영 판단자다.

회의록 항목 각각에 대해, 프로젝트 그래프에 어떻게 반영할지 판정하라. 이 그래프는 프로젝트의 **확정된 결정과 그 실행 이력만** 담는다. 회의록에는 모든 항목이 이미 보존되어 있으므로, 그래프에서 제외해도 정보는 사라지지 않는다.

**핵심 원칙: 잘못된 반영이 누락보다 나쁘다.** 확실할 때만 그래프에 넣어라. 애매하면 MINUTES_ONLY다.

## 판정 종류

| 항목 type | 허용되는 판정 |
| --- | --- |
| DECISION | `NEW_DECISION` 또는 `MINUTES_ONLY` |
| ACTION | `ATTACH`, `UPDATE_ACTION`, 또는 `MINUTES_ONLY` |
| ISSUE | `ATTACH` 또는 `MINUTES_ONLY` |

- 입력 items의 **모든 항목에 대해 판정을 정확히 1개씩** 출력한다. 누락·중복 금지.

## attachTo 규칙 — 위반 시 판정 무효

`attachTo`에 올 수 있는 값은 다음뿐이다:

- **ACTION 항목**: 이번 items 중 NEW_DECISION으로 판정한 DECISION의 id (예: "m1"), 또는 candidates 목록의 decisionId (예: "D-M1-03")
- **ISSUE 항목**: 위 두 가지 + 이번 items 중 ATTACH로 판정된 ACTION의 id (예: "m2"), + candidates에 동봉된 **기존 액션의 actionId** (예: "A-M2X-02" — 기존 액션에서 파생된 문제를 그 액션에 붙임)

절대 금지:
- candidates에 없는 decisionId/actionId를 만들어내는 것
- 붙일 결정이 없는 ACTION/ISSUE를 위해 **존재하지 않는 결정을 지어내는 것** → 반드시 MINUTES_ONLY
- MINUTES_ONLY로 판정된 항목에 다른 항목을 붙이는 것

## 기존 액션 갱신 (UPDATE_ACTION) — PoC 2차

candidates의 각 결정에는 하위 **기존 액션(actions: actionId, title, status)** 이 동봉될 수 있다. 후속 회의에서 그 기존 액션의 상태가 바뀌면 새 액션을 만들지 말고 UPDATE_ACTION으로 판정한다.

- **[기존 액션 갱신]** 기존 액션의 기한 변경, 담당 변경, 상태 변경(완료·시작·중단·취소), 진행 중인 작업의 세부 보완은 **UPDATE_ACTION**이다. 새 액션을 만들지 마라.
- **[새 액션]** 새로운 구현 작업, 기존 작업과 독립적인 후속 작업, 검증을 위한 별도 작업은 **새 액션(ATTACH)** 이다. 기존 액션의 UPDATE로 처리하지 마라.
- **[판별 기준]** 그 발화가 기존 액션 제목이 가리키는 **같은 실행 단위**에 대한 것인가? 같은 결정 밑이라도 실행 단위가 다르면 새 액션이다.
- **[완료 액션 재개 금지]** 완료된 액션은 되살리지 않는다. 완료 이후의 후속 작업은 항상 새 액션이다. (예: "초안 공유 완료" → 기존 액션 UPDATE(완료), "피드백 반영해 확정" → 새 액션)

UPDATE_ACTION 필드:
- `targetActionId`: candidates에 동봉된 기존 액션의 actionId (그 목록에 없는 id 금지).
- `changes`: 허용 키는 `status`, `dueDate`뿐. `status` 값은 `COMPLETED` / `IN_PROGRESS` / `CANCELLED`. 기한 연기는 `dueDate`.

## 판단 지침 (팀 확정 규칙)

**[확정성 판별 — 가장 중요]** 어떤 선택이 발화된 뒤 팀의 다음 행동을 보라.
- 다음 행동이 **그 선택을 검증하는 것**("되는지 테스트해보고")이면 → 확정 아님 → MINUTES_ONLY (reason: NOT_CONFIRMED). 그 선택에 딸린 이슈·검증 작업도 전부 MINUTES_ONLY.
- 다음 행동이 **그 선택 위에서 구현을 진행하는 것**("그럼 컨슈머 구현할게요")이면 → DECISION 확정 → NEW_DECISION.

**[암묵적 동의]** 제안이나 조사 결과 공유 후 반대 없이 그것을 전제로 진행되면 확정된 결정으로 인정한다.
구분 기준: 그 내용에 대해 **추가 검증이 다음 행동으로 남아 있으면** [확정성 판별]에 따라 NOT_CONFIRMED, **검증 없이 방침으로 받아들여지면** 확정.

**[잠정 합의]** "해 볼까요?", "좋을 것 같아요" 수준의 반응만 있고 실행 착수가 명확하지 않으면 NOT_CONFIRMED. 기술 검증이 전제 조건으로 남아 있으면 NOT_CONFIRMED.

**[개인 계획]** 한 사람이 자기 계획을 선언한 경우, 뒤따르는 팀의 동의 발화가 있으면 인정하고, 없거나 애매하면 NOT_CONFIRMED. 원문 세그먼트에서 해당 발화 이후의 반응을 확인하라.

**[전달 화법 — 외부 방침에 한정]** "~라 하더라", "~라고 하셨다"로 전달된 내용 중, **팀 외부 인물(컨설턴트, 코치, 강사, 운영진 등)의 지시·방침·요구**는 정보 공유다 → NOT_CONFIRMED. 팀이 그에 따라 스스로 정한 행동만 별도로 인정한다.

단, **팀원이 자신의 조사 결과를 전달하는 것**(AI 도구에 물어본 결과, 문서·레퍼런스 조사, 실험 결과 공유 등)은 외부 방침이 아니라 근거 제시다. 조사 결과 공유 후 반대 없이 그것을 전제로 진행되면 [암묵적 동의] 규칙에 따라 확정된 결정으로 판정한다. 전달 화법이라는 이유만으로 NOT_CONFIRMED로 판정하지 마라.

**[촉발 이슈의 귀속]** 어떤 이슈가 논의되다가 같은 회의에서 그 이슈를 해소하거나 다루는 결정이 나오면, 그 이슈는 해당 결정에 ATTACH한다. 결정의 리스크를 지적하는 이슈도 그 결정에 ATTACH한다. 기존 액션에서 파생된 문제라면 그 기존 액션(actionId)에 ATTACH한다.

**[미채택 안]** 제목에 "— 미채택"이 붙은 항목은 MINUTES_ONLY (reason: NOT_CONFIRMED).

**[기존 결정 연결]** ACTION/ISSUE가 candidates의 기존 결정을 실행·구체화하거나 그 결정에서 파생된 문제를 다루면 해당 decisionId에 ATTACH한다. 단, 주제 어휘가 겹친다는 이유만으로 붙이지 마라 — 그 결정의 **실행이나 결과와 직접 관련**되어야 한다. 후보가 여러 개면 내용상 가장 직접적인 하나를 골라라. 확신이 없으면 MINUTES_ONLY (reason: LOW_CONFIDENCE).

## MINUTES_ONLY reason

| reason | 사용 시점 |
| --- | --- |
| NO_RELATED_DECISION | 새 결정도 없고, candidates에 관련 결정도 없음 |
| LOW_CONFIDENCE | candidates에 후보는 있으나 연결 확신 부족 |
| NOT_CONFIRMED | 확정되지 않은 논의: 조건부 선택, 잠정 합의, 보류, 미채택, 전달된 외부 방침, 동의 없는 개인 계획 |

## 입력

### 회의록 항목 (판정 대상)
```json
[
  {
    "id": "m1",
    "type": "DECISION",
    "predictedCategory": "BACKEND",
    "title": "소음 전처리 파이프라인 도입",
    "content": "STT 앞단 전처리.",
    "evidence": [
      {
        "segmentId": "seg-1",
        "quote": "소음 전처리는 CLOVA STT 전에 넣는 걸로 결정합시다."
      }
    ]
  },
  {
    "id": "m2",
    "type": "ISSUE",
    "predictedCategory": "BACKEND",
    "title": "레디스 캐시 도입 여부 미확정",
    "content": "도입 여부 보류.",
    "evidence": [
      {
        "segmentId": "seg-2",
        "quote": "Redis 캐시 도입은 나중에 다시 논의해 봐야 할 것 같아요."
      }
    ]
  }
]
```

### 기존 결정·액션 후보 (이전 회의들에서 확정. 각 결정에 하위 actions가 동봉될 수 있음. 비어 있을 수 있음)
```json
[]
```

### 회의 전체 원문 (문맥 확인용 — 확정성·팀 반응·실행 단위 판단에 사용)
```json
[
  {
    "segmentId": "seg-1",
    "startMs": 1000,
    "speakerLabel": "SPK_1",
    "text": "소음 전처리는 CLOVA STT 전에 넣는 걸로 결정합시다."
  },
  {
    "segmentId": "seg-2",
    "startMs": 5000,
    "speakerLabel": "SPK_2",
    "text": "Redis 캐시 도입은 나중에 다시 논의해 봐야 할 것 같아요."
  }
]
```

## 출력 형식

JSON 하나만 출력한다. 설명, 마크다운, 코드펜스 없이 JSON 객체만.

```json
{
  "meetingId": "<입력의 meetingId>",
  "judgments": [
    { "itemId": "m1", "result": "NEW_DECISION", "category": "BACKEND" },
    { "itemId": "m2", "result": "ATTACH", "attachTo": "m1 또는 decisionId 또는 actionId" },
    { "itemId": "m3", "result": "UPDATE_ACTION", "targetActionId": "A-M2X-01", "changes": { "status": "COMPLETED" } },
    { "itemId": "m4", "result": "MINUTES_ONLY", "reason": "NO_RELATED_DECISION | LOW_CONFIDENCE | NOT_CONFIRMED" }
  ]
}
```

- NEW_DECISION에만 `category` (BACKEND / FRONTEND / INFRA / AI / DESIGN / PLANNING)
- ATTACH에만 `attachTo`
- UPDATE_ACTION에만 `targetActionId` + `changes` (키: status / dueDate)
- MINUTES_ONLY에만 `reason`

## 예시 1 — 새 결정 묶음 (candidates 없음)

items:
```json
[
  {"id": "m1", "type": "DECISION", "title": "로그인 인증에 JWT를 사용한다"},
  {"id": "m2", "type": "ACTION", "title": "JWT 인증 필터를 구현한다"},
  {"id": "m3", "type": "ISSUE", "title": "Refresh Token 재사용 공격 대응 필요"},
  {"id": "m4", "type": "ISSUE", "title": "소셜 로그인 도입 여부 미확정"}
]
```
candidates: `[]`

출력:
```json
{
  "meetingId": "ex-meeting",
  "judgments": [
    { "itemId": "m1", "result": "NEW_DECISION", "category": "BACKEND" },
    { "itemId": "m2", "result": "ATTACH", "attachTo": "m1" },
    { "itemId": "m3", "result": "ATTACH", "attachTo": "m2" },
    { "itemId": "m4", "result": "MINUTES_ONLY", "reason": "NOT_CONFIRMED" }
  ]
}
```

## 예시 2 — 기존 액션 갱신 vs 새 액션 (같은 결정 밑 대비 쌍)

items:
```json
[
  {"id": "m1", "type": "ACTION", "title": "SQS 컨슈머 구현 완료"},
  {"id": "m2", "type": "ACTION", "title": "메시지를 꺼내 처리하는 로직 신규 구현"}
]
```
candidates:
```json
[
  {"decisionId": "D-77", "title": "비동기 처리는 AWS SQS를 사용한다", "category": "INFRA", "status": "ACTIVE",
   "actions": [{"actionId": "A-10", "title": "SQS 컨슈머와 재시도 로직 구현", "status": "IN_PROGRESS"}]}
]
```
원문(참고): "컨슈머 구현 끝났습니다." / "이제 메시지 꺼내서 처리하는 부분을 새로 구현해야죠."

출력:
```json
{
  "meetingId": "ex-meeting-2",
  "judgments": [
    { "itemId": "m1", "result": "UPDATE_ACTION", "targetActionId": "A-10", "changes": { "status": "COMPLETED" } },
    { "itemId": "m2", "result": "ATTACH", "attachTo": "D-77" }
  ]
}
```

m1은 기존 액션 A-10("컨슈머 구현")의 **같은 실행 단위**가 완료된 것이므로 UPDATE_ACTION(status COMPLETED)이다. m2는 같은 SQS 결정 밑이지만 "메시지 처리 로직"이라는 **다른 실행 단위**의 신규 작업이므로 A-10의 UPDATE가 아니라 새 액션(D-77에 ATTACH)이다. 컨슈머 구현이 완료됐다고 해서 그 액션을 되살려 새 작업을 붙이지 않는다.


### 서버 확정 요청 식별자
최상위 `meetingId`는 아래 값을 복사해 정확히 일치시켜라.
```json
{
  "meetingId": "M-CHAIN"
}
```
